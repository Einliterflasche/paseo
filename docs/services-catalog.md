# Services catalog and authenticated previews

The Services catalog adds a host view, workspace panel and individual web-preview tabs using the existing workspace directory and script lifecycle APIs. The catalog, authenticated preview flow and registration actions are exercised against isolated daemons and compiled packages. Firefox and Chromium checks cover the configured front, daemon, separate gateway and a real managed React/Vite service. Production installation and continuity remain unproved.

`EXPO_PUBLIC_PASEO_SERVICES_CATALOG=1` opts a bundle into the catalog. Default builds remain off, including the Nix package's `servicesCatalog = false` default. Preview operations additionally require the current physical connection's advertised preview registry. Do not put feature options in the daemon's core JSON configuration: older daemons reject unknown fields. Saved preview policy uses a separate versioned file.

The host view selects one host explicitly. The workspace panel filters the same catalog by workspace ID. Entries include configured managed services and explicitly registered existing local web services; ordinary one-shot scripts are excluded. Existing directory synchronization owns pagination, reconnect and status updates. Visible catalog surfaces acquire its subscription demand, including on native without the sidebar. Hidden retained panels release demand. Search remains local component state. Grid/list choices persist separately per host/workspace under `@paseo:services-preferences:v1:` keys. Reads preserve invalid values and expose a retry; explicit changes serialize through the existing query/mutation owner and publish only after the write succeeds. The latest write outcome is shared independently of mutation history, so a recovered failure cannot reappear when a writer unmounts. Preference failures do not change service lifecycle authority.

Listing does not start services, probe apps, mount iframes or create thumbnails. Cards show placeholders. Legacy proxy URLs are deliberately omitted from the catalog projection. In the isolated build, matching registered routes advertised by an eligible physical control connection offer Open preview. Opening reveals the service's workspace tab and explicitly prepares a one-use ticket; merely mounting a panel never issues Open. The control-only listener never selects legacy service routes. Separately configured public listeners retain their existing routes; preview failures never fall back to them.

Start and Stop use the daemon's advertised `workspaceScriptManagement` capability and existing authorization. They are explicit mutations with retries disabled. Lost acknowledgements remain errors; Refresh only reconciles the directory. It never resends a lifecycle mutation. Logs use the existing terminal view. Accessible button names include the service and workspace context so repeated cards remain distinguishable. Terminal lifecycle and reachability are distinct: Started means the script runtime is active; absent health data means Health unknown.

Reconnect keeps cached cards visible and disables lifecycle actions until the existing directory owner commits a snapshot for the current client generation and connection epoch. A skipped or failed refresh cannot clear an uncertain action. Automatic directory failures end loading and display the owner's error; unavailable capability has a separate explanation. The client rejects an observed terminal replacement before sending Stop. The existing Stop API addresses a script by workspace and name; it cannot atomically guarantee stopping only the displayed run if replacement occurs after dispatch. That stronger guarantee requires a separate lifecycle-owner precondition.

Both catalog tabs and individual service-preview tabs are ephemeral. The shared persisted layout schema is unchanged, and the persistence boundary removes Services tabs before writing. Older clients otherwise delete the entire layout entry on unknown tab kinds. Normal agent, terminal and file tabs remain. Sidebar preferences already use extensible string keys; an unavailable Services preference is ignored while unrelated preferences survive.

The web-only resident preview host owns iframe documents above workspace-screen eviction and theme remount boundaries. Existing layout actions own preview tab order, split and close; disposable pane anchors only position the document. Browser renderer evidence covers moving, splitting, reordering, compact overlays, resizing, rapid reopen and loading during an existing transition. The Open coordinator is integrated with this owner. Isolated full-app Chromium and Firefox evidence covers authenticated HTML/React, Vite Fast Refresh, preserved document/draft state, standalone tabs and workspace Close without stopping the service.

The coordinator captures the client generation and connection epoch, uses a fresh attempt ID for each explicit Open, and never queues Prepare or Close behind a future connection. Closing a workspace preview tab releases its embedded contribution; moving or hiding it does not. Standalone browser previews have a separate root-owned contribution and survive workspace tab Close. Use Close browser preview in the pane or catalog card to release that contribution explicitly; unobserved browser-tab disappearance is governed by source lifetime. Source loss preserves the document and presents an explicit Open action. For an existing document at the registered service path, Open confirms fresh authority in a disposable hidden frame without navigating that document. The attempt owns the helper and removes it on completion, cancellation or source loss. Reload is a separate explicit navigation and can discard unsaved app state. A separate non-secret browser profile handle is read under a Web Lock at every Open. Invalid storage and superseded sessions have explicit recovery; tickets are never persisted. Pending loads can be cancelled without closing the tab. Native keeps an unavailable preview fallback.

Cancel stops pending initial Open or Reload navigation without removing the resident iframe. A delayed confirmation cannot navigate it afterward, even while another control page keeps the service authorized. Normal Vite Fast Refresh preserves component state. After source disconnect, the retained worker restriction blocks stock Vite's reconnect helper: Open restores API access and preserves the document, while explicit Reload restores HMR and resets that document's local state. Do not describe this as automatic HMR recovery.

The optional gateway handles ticket POST, cookie confirmation, registered HTTP streams and WebSocket upgrades. Confirmation returns a nonce-protected document that starts a fresh application navigation for initial Open and explicit Reload; this preserves Firefox's same-origin metadata. A reauthorization helper confirms authority without that final navigation. Wire tests cover held handshakes, EOF, resets, shutdown, framing and backpressure. Actual isolated Chrome/Firefox flows also serve React through Vite, including API/forms and Fast Refresh preserving page state. These checks are separate from deployment proof. Bootstrap can create the feature from the opt-in transport environment and saved policy; absent that environment, existing bootstrap behavior is unchanged. Explicit fixture injection and configured transport cannot both own the feature.

Preview login accepts exactly the 50-byte form generated by Paseo: literal `ticket=` followed by the canonical 43-character base64url credential. The user approved this login-only contract. Percent-encoded equivalents, empty fields and extra bytes are rejected as they arrive, without consuming the ticket or buffering an unfinished body. Application and service uploads keep their existing behavior.

The operator approved a 60-second unused Open deadline and a 15-second gateway watchdog on broker nonresponse. The broker deadline starts at reservation and covers delivery, redemption and pending confirmation; active contributions have no additional fixed expiry while their source remains eligible. Monotonic checks reject expired work even if a timer runs late. A delayed result cannot revive an expired attempt. A prepared browser-tab action returns to idle at its server-supplied deadline and requires a fresh explicit Open. Expiry never prepares or submits another ticket automatically. A separate-process fault fixture stops the broker and observes active HTTP/WebSocket connections close before the broker resumes. That proves the direct Unix-socket path; the front-proxy path has its own fault test. These authorization lifetimes never delete stored service definitions or history.

Registered metadata is delivered in an optional, source-specific `server_info.servicePreviews` projection. Incapable siblings sharing a session do not inherit it. The registry is authoritative for service IDs and endpoints; the browser never supplies a forwarding port. External registration persistence is an inert, separate versioned atomic store at `services/registrations-v1.json`, retaining archived definitions and malformed/unknown-version files. An optional owner and source-bound RPC dispatcher now connect this store to Register, Enable preview and Remove actions. Registration saves an inactive definition; Enable is a separate explicit action. Remove revokes forwarding and archives the definition without terminating or adopting the process. Stale workspace/infrastructure entries remain listed and removable; they cannot activate. Failed revalidation invalidates an existing binding, and initialization rollback only invalidates routes acquired by that owner.

Managed service previews are enabled automatically when their runtime and endpoint appear. The default route removes the reserved service prefix before forwarding upstream, and the UI has no enable/settings or mount-mode controls. Existing saved records and operator policy can still use `preserve` for compatibility. The older managed Enable/Disable protocol and its separate `services/managed-enrollments-v1.json` store remain readable for compatible clients, but the current catalog does not require that setup step. The card's preview surface opens the service in a workspace tab; its three-dot menu contains the separate Open in new tab action.

Registration forms preserve edits across reconnect and capture the current connection separately for each explicit Submit. External action reservations and outcomes are shared per host/service above card lifetime, so grid changes and filtering cannot permit a duplicate pending action or erase its failure. Neither surface retries a mutation automatically.

Preview Enable, Register and Connect share the host's restart admission gate. If agent recovery is paused, resolve the recovery error shown in the host banner before attempting fresh setup; reconnecting alone does not reopen admission. Disable, Disconnect and Close remain available to reduce preview access. This does not bypass or repair an agent checkpoint.

The optional ingress claims the reserved namespace before Express and uses one upgrade dispatcher. A structural authority port and dedicated IPC implementation separate the broker from gateway stream ownership. The Unix-socket worker's parent retires preview authority when the worker ends; it never restarts that worker or reuses its broker automatically. An independent Caddy front sends the reserved prefix directly to the gateway socket and ordinary traffic to the private daemon listener. Preview bytes therefore bypass the broker event loop. The front preserves the raw target; the daemon's reserved ingress rejects encoded/dot/slash aliases before its SPA. This pairing is required even with forwarding disabled.

The feature owner connects managed runtime changes, endpoint changes and workspace archival to revocation. Saved stopped enrollments do not start processes. A workspace becoming unavailable blocks fresh activation, ends existing contributions and waits for gateway teardown before its registry write commits. Failed revocation leaves the previous registry state intact. External Disconnect reserves its archival write before publishing synchronous invalidation, so a shutdown started by a subscriber still drains that accepted write. Feature shutdown drains owned persistence and closes the gateway without stopping the application process. A broker-only failure also retires its gateway child, and archival waits for actual child exit before committing. Daemon shutdown starts preview retirement immediately but saves agents and tears down ordinary transport before awaiting the optional feature drain. Preview cleanup failures are reported without turning an intended daemon shutdown into a supervisor crash restart. Archival waits for actual gateway teardown after authority failure; a child that ignores termination can keep that archival pending. No new termination timeout or forced-kill escalation is added.

## Memory ownership and OOM priority

Managed service programs and the preview gateway run in separate OS processes with separate V8 heaps. Their allocations do not consume the daemon's V8 heap limit. The daemon does retain preview authorization metadata; browser documents and UI state belong to the browser. Same-origin embedded documents can share a browser renderer with Paseo, so there is no per-iframe memory or OOM isolation. The server's Linux priority does not protect that browser renderer from a runaway page. Application HTTP/WS bytes stream through the gateway, not through daemon IPC. A V8 heap-limit failure aborts the affected process independently of the Linux OOM killer; changing kill priority cannot prevent a daemon heap-limit failure.

Children launched by Paseo inherit its systemd cgroup, so their memory contributes to the unit's total accounting and any configured cgroup budget. Registering an already-running external service does not move it into that group or change its process settings. `PASEO_DAEMON_HEAP_MB` configures only the daemon worker's old-space allowance; it does not set service or gateway heaps. See [fork maintenance](fork-maintenance.md) for the installed configuration. The development default is not an installed-daemon guarantee.

On Linux, newly launched managed service shells set `oom_score_adj=1000` before running shell startup files or service code; descendants inherit it. The gateway sets the same preference before accepting traffic. If Linux refuses the score write, that process fails startup rather than silently starting without the requested preference. Parent processes and ordinary terminals are unchanged. The Nix module uses `OOMPolicy=continue` so losing one child to the kernel OOM killer does not instruct systemd to stop all agents. This prefers sacrificing services when the kernel selects an OOM victim; it cannot prevent earlier swap pressure, a V8 abort, or a policy that kills an entire cgroup. A killed managed service can be started again from the catalog. Loss of the gateway retires preview authority for that daemon lifetime; preview recovery then requires the controlled restart path, while ordinary Paseo remains available. Existing externally launched programs retain their owner's policy. No new memory quota, retained-data expiry or eviction of live preview documents is added.

Standalone controllers keep authority alive across card/panel unmounts while an Open is pending or active. Once idle or failed and no UI uses them, their owner releases the controller and its source subscriptions. Local Open errors are discarded with that unused controller; an unobserved Close failure still reaches the root notification. An active standalone contribution remains until explicit Close or source invalidation. Completed broker activations release their route captures before cancellation callbacks; old guards remain terminal. Session/cookie identity and per-source replay tombstones intentionally remain while the broker can admit work, to prevent replaced sessions and used attempt IDs from reviving. They are small records, but not a bounded-memory policy; distinct profile/source activity still grows retained identity data. Closing the broker releases its maps without changing stored registration files.

## Optional deployment configuration

These settings describe the candidate topology, not permission to activate it. The continuity preflight and actual package/rollback rehearsal remain required before changing the live service.

The NixOS module's `services.paseo.previews.enable` keeps the existing `services.paseo.port` as the independently supervised loopback front and moves the daemon to `previews.daemonPort` (default 6768). It requires `listenAddress = "127.0.0.1"`, distinct ports and `previews.controlOrigin` set to the exact existing HTTPS origin. The module's default package includes the opted-in catalog. A custom package must be built with `servicesCatalog = true`. Startup ordering waits for the replaced daemon to release the front port. The front has no unit dependency that stops it when the daemon or gateway exits. Existing HTTPS ingress and its advertised address remain unchanged.

The module supplies `PASEO_SERVICES_FRONT_PORT`, `PASEO_SERVICES_GATEWAY_SOCKET` and `PASEO_SERVICES_CONTROL_ORIGIN`. These nonpersisted transport settings reserve `/__paseo_services/` and enforce control-only authority routing even when preview policy is disabled or invalid. The front and private daemon validate one unambiguous Host against the configured public authority or the specific loopback authorities needed by CLI connections; forwarded headers cannot select a service. Enabled preview policy must match that control origin. A legacy public route that depends on the listener being converted causes startup refusal until it has a separate intentional listener. The gateway socket is `/run/paseo-previews/gateway.sock`; startup never removes an existing path to force a bind. The daemon, front and legacy proxy TCP ports are excluded from registration. Invalid feature state leaves ordinary Paseo available and forwarding closed.

Keep operator policy at `$PASEO_HOME/services/policy-v1.json`. The Nix module does not overwrite it. Missing policy defaults off; malformed or unknown-version files are retained. An enabled policy has this shape:

```json
{
  "version": 1,
  "enabled": true,
  "controlOrigin": "https://your-existing-paseo-address.example",
  "managedServices": [
    {
      "workspaceId": "the-existing-workspace-id",
      "scriptName": "web",
      "name": "Web app",
      "mount": "preserve"
    }
  ]
}
```

Use the exact existing HTTPS origin, including any nondefault port. Each application must support its stable prefix and chosen mount contract. `preserve` forwards the full prefix; `strip` removes it upstream and still requires the application to produce compatible public URLs. Policy and password changes are restart-bound. The `managedServices` array is an optional compatibility override; ordinary managed services receive a stripped preview route automatically. External services are registered through the authenticated catalog, then activated by a separate explicit action. Adding an application never edits the front configuration.

The packaged front configuration is generated from `service-preview/front-config.ts` and tested with Caddy 2.11.2. It preserves Host, request targets and the existing trusted loopback forwarding scheme; has no stream deadline, proxy retry policy or whole-body buffering; and does not interpret application `X-Accel-*` headers. TLS storage cleaning is explicitly disabled: this HTTP-only front must not delete other Caddy data owned by the same user. HTTP request loggers are excluded because cancellation warnings also contain request targets and headers. Process/configuration failures remain logged. Its configuration generator is independent of the daemon package, so a daemon update does not change the front unit.

A daemon-only rollback keeps the front installed and both listeners on their assigned ports. Its target must retain the reserved-ingress guard and understand the private-listener transport settings. The rollback target also needs control-only authority handling, the matching control origin, and the private-listener configuration. It must read the current shared-log checkpoint format and preserve the consumed-generation failure state described in [restart recovery](restart-recovery-plan.md). A pre-feature package lacks the ingress guards; earlier Services candidates also predate that checkpoint update. Retaining Caddy alone does not establish a safe rollback to either. Rehearse the exact compatible rollback package and checkpoint before production handover.

The catalog UI uses cross-platform components, the existing launcher/panel registry, theme tokens and shared controls. Native typechecking is required; this development checkpoint does not claim device validation.

## Validation

Run only the relevant files, with `--bail=1`, following the repository's test resource rules:

```sh
npm run test --workspace=@getpaseo/app -- --project unit \
  src/services/catalog.test.ts src/services/catalog-state.test.ts \
  src/services/preferences.test.ts \
  src/services/persistence.test.ts src/sidebar-nav/model.test.ts \
  src/i18n/resources.test.ts --bail=1
npm run typecheck --workspace=@getpaseo/app
```

Unit checks use explicit runtime and storage ports with typed adapters and real query/mutation observers. They do not mount components or mock application modules. The storage seam in the workspace layout factory preserves its existing default and schema.

For ordinary internal Chrome UI checks, use the user-selected Jev browser skill and inspect its screenshots plus independent outcomes. Use direct tools when its limitations prevent the required frame, timing or protocol checks, and perform final Firefox validation. Product test/model fixtures remain offline.

The opt-in `e2e/browser/services-catalog.spec.ts` exercises a real isolated daemon, real Chromium, service Start/Stop, host/workspace navigation, persistence, offline UI, feature-off behavior and automatic directory failure/recovery, preference read recovery and real browser storage-quota failure/recovery. It preserves fixture files. The initial VM run uses a separate loopback-constrained Metro harness under `.dev/services/`; all logs, failures, screenshots and immutable review input are retained. Expo's `--localhost` advertising option alone does not constrain this checkout's Metro listener, so do not assume an ordinary Expo command is private.

The host picker replaces the owning `h/[serverId]` route and its Services child together. A leaf replacement can update the URL while retaining the old host context. With this Expo version, parent navigation can instead carry the old nested state into the new host. The browser regression checks the URL and selected host through both directions and repeated sidebar navigation.

Persistence checks include an actual candidate web bundle → older installed bundle → candidate bundle round trip in one isolated browser profile. Ordinary file tabs, pane geometry, settings and Services preferences survive the older UI's read and focus rewrite. Ephemeral Services tabs stay absent from saved layouts. The candidate daemon runs continuously; this establishes UI storage compatibility, not daemon rollback or a deployment rehearsal.

## Remaining gates

General load/admission qualification, installed exposure checks, supervisor handover, native device validation and continuity remain. Compiled bootstrap, front/gateway routing and Firefox/Chromium preview checks are qualified to their recorded source versions. Native development JS bundles select the non-web fallback, but do not establish device behavior. The user chose one trusted VM boundary and the existing Paseo address, with no additional domain. Strong process-generation binding is therefore retired. Forwarding still requires verified physical-source admission, shared browser/service authorization, terminal revocation, exact registered loopback routing, tested path mounts and gateway containment. Same-origin service/Paseo storage is intentionally shared; no malicious-service isolation is claimed.

Every production install, even with the feature off, requires the checkpointed path in [fork maintenance](fork-maintenance.md), plus installed transport and restored-generation verification. The deployment CLI refuses replacement while any terminal or managed service is live; it checks again under the prepared daemon's frozen admission. This permits qualification of a handover with no endangered terminals, without claiming transfer or survival of running managed services. Other owned processes and intentional public listeners still need their deployment-specific inventory and continuity checks. Thumbnail capture remains separate; cards do not silently contact applications.
